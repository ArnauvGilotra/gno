## Goal & Context

Defects that surfaced during the GNO 2.11.0 release and rollout (2026-10-11/12), plus the follow-ups that release left open. Each one was reproduced on origin/main (2.11.0) in an isolated environment; repro scripts and logs are in `~/.cache/agent-work/fn220-research/` (local to Thor). One spec, one PR, released as 2.11.1.

### Index safety and install targets (from the rollout)

1. **Opening an index with a different config deletes collections.** `syncCollections` (src/store/sqlite/adapter.ts) deletes every `collections` row the opening config does not list, and `documents` cascades (`ON DELETE CASCADE`, `PRAGMA foreign_keys = ON`). It runs on every open: CLI `initStore` (src/cli/commands/shared.ts), SDK `createGnoClient` (src/sdk/client.ts), scoped index, resident runtime, sessions, config refresh. So a read-only command such as `gno --config other.yml search x`, or an SDK client given a config but no `dbPath`, silently wipes the default index's other collections. This happened on Thor on 2026-10-11 23:41 UTC: a QA script opened the real index with a two-collection sandbox config and every real collection's documents were deleted (rebuilt by `gno update` + `gno embed`). The behavior has existed since the first store schema. Reproduced with two SDK clients on one temp index (1 doc → 0 docs). `gno cleanup` (src/cli/commands/cleanup.ts:67) deliberately runs the same deleting sync, so `gno --config sandbox.yml cleanup` drops every collection the sandbox config does not list without naming them.
2. **`gno agents update` installs where no block exists.** Its help says it refreshes an installed block, but `installAgents(opts, "update")` plans `install` for harness files without a block. On a machine whose harness files carry a user-managed GNO block (Gordon's canonical instructions), `update` would append a second, generic ladder and create `~/.hermes/SOUL.md` where none exists.
3. **`gno skill install --scope user` ignores `CLAUDE_CONFIG_DIR` and `CODEX_HOME`.** src/cli/commands/skill/paths.ts:153 joins `homedir()` (or `GNO_SKILLS_HOME_OVERRIDE`) with `.claude`/`.codex`; `gno agents` (src/cli/commands/agents/harnesses.ts:84-91, 193) honors both variables. Profile directories (e.g. `~/.claude-instances/*`, `~/.codex-instances/*`) never receive the skill: 13 profile copies across three hosts stayed stale in the 2.11.0 rollout.

### A missing collection root is invisible outside `gno update`

4. 2.11.0 keeps a collection's documents when its root folder is missing and `gno update` prints `[SOURCE_AVAILABILITY_UNKNOWN] Collection root could not be resolved (ENOENT ...); indexed documents were kept`. Afterwards `gno status` shows the collection as normal (`notes: 1 docs, 1 chunks`) plus only `Recent errors: 1 (last 24h)`, `gno status --json` has no per-collection error, and `gno doctor` reports `Overall: HEALTHY`. The Web UI status (src/serve/status.ts:267) likewise only counts recent errors. A user whose Drive or external disk is unmounted cannot see which collection is stale or why.

### Search speed and the Web UI's Fast mode

5. **`gno search` with a long question takes seconds.** FTS5 `snippet()` sits inside the `fts_matches` CTE (src/store/sqlite/adapter.ts:3146), so it re-tokenizes the whole body of every matched document before ORDER BY/LIMIT. Documents average 21 KB (max 1.3 MB) and multi-word AND queries match the longest ones. On a copy of Gordon's index: ranking alone 27-88 ms, with `snippet()` 1.5-6.0 s at the SQL level; CLI `gno search` on a long question 0.75-1.4 s at `-n 5` and 3.3-6.9 s at `-n 20` (the `--json` default); the same queries with `--line-numbers` (no snippet) 160-200 ms. Moving `snippet()` after LIMIT saved 0-60% because these queries match only 18-47 rows. Building the snippet in JS from the stored chunks of the final top-N documents measured 123-171 ms end to end with unchanged ranking. Separately, `snippetRange` always comes from chunk seq 0 while the FTS window can be anywhere in the document, so the line span shown with a snippet can be wrong.
6. **The Web UI "Fast" depth is keyword-only and slower than CLI/MCP fast.** `ThoroughnessSelector.tsx:32` labels Fast as BM25 and `Search.tsx:326-331` sends it to `/api/search` unless query modes or intent are set; CLI `--fast` and MCP `fast` are hybrid without expansion, rerank and graph (`resolveDepthPolicy`, src/core/depth-policy.ts). Measured on a sealed `gno serve` with vectors: UI Fast on long questions 674-1,175 ms returning 7-12 results; `/api/query` with `noExpand`/`noRerank`/`noGraph` 95-126 ms returning 20 results with `vectorsUsed=true`. docs/WEB-UI.md (lines ~196-202, ~688-694) still describes BM25/Vector/Hybrid mode choices the UI no longer offers.

### Agents miss supersession and dates in compact Capsules

7. **The compact agent projection drops `supersededBy` and the content date.** MCP `gno_context` sends the `gno-context-agent-v1` projection as its only model-visible text (src/mcp/tools/context.ts:299). `projectContextCapsuleForAgent` (src/app/context-agent-projection.ts:96-108, 270-282) builds an 11-position evidence entry that copies neither `supersededBy` nor `documentDate`, although the full Capsule evidence carries both (src/core/context-evidence.ts:495-505). An agent reading the text cites a superseded memory fact as current. The Markdown Capsule and the answer prompt already show both. The tuple positions are a versioned contract (spec/mcp.md:531-557; tests test/context/cross-surface-parity.test.ts:589, test/eval/agentic/context-capsule-demo.test.ts:115; evals/agentic/promotion.ts:129,156 requires v1 and 11 positions). Related: in the repro, memory facts had `documentDate = null` in Capsule evidence although their frontmatter carries `memory.createdAt`, so the record date 2.11.0 promised for `ask` may not reach Capsule evidence (or ask sources) for memory facts.

### Evals that do not measure anything

8. **`bun run eval:memory` hangs.** Under evalite's vitest module runner, Bun-only `import.meta.path`/`import.meta.dir` are undefined. `src/ingestion/file-processor.ts:287,450` calls `isBunfsPath(import.meta.path)` → `src/serve/spa-production-build.ts:83` throws on `path.replaceAll` → indexing fails with `MEMORY_SYNC_FAILED ... Could not start the file processor`. Evalite 1.0.0-beta.16 then crashes in its reporter (`options.task?.file.pool`, evalite/dist/reporter/rendering.js:75, a vitest 4 `TestCase` shape mismatch), so `vitest.close()`/`process.exit()` are never reached and the process hangs; any eval that throws hangs the same way. Broken since 4cb63dce (v2.8.3, 2026-09-27). With `isBunfsPath` accepting a non-string, the memory gate ran 19/19 in about 1 s. CLI, MCP and serve always run under Bun and are not affected.
9. **`ask.eval.ts` scores 50% with 0 citations on every case.** Since a001949d (2026-07-23) `generateGroundedAnswer` (src/pipeline/answer.ts:568) skips sources without `sourceHash`/`mirrorHash` or a hash-verified passage; the eval's mocks (evals/ask.eval.ts ~133) carry none and pass `store: null`, so no model is ever called and the score is the skipped judge (1) plus zero citations. After fixing the mocks, generation fails with `INFERENCE_FAILED: Native worker failure: exited` because src/llm/native-worker/client.ts:317,331 use `import.meta.dir` (undefined under vitest) and the catch around line 300 hides the TypeError. With both fixed the eval scored 77% offline and 15 of 24 cases cited. Residual signal, out of scope: the balanced preset (Qwen2.5-3B) answers without `[n]` markers on 7 of 8 cases and abstains.
10. **The agentic eval `--write` lane cannot pass.** `evals/agentic/lifecycle/gno-mcp.ts:199` counts `content_vectors WHERE model = ?` after a real `gno embed`, but since 2.7.0 embeddings live in `vector_variants` under an activated partition (`test/cli/vec-partition.test.ts:101` asserts `content_vectors` stays empty). Isolated repro: `gno_vector_preparation_mismatch ... vectors=0 chunks=34` while `getStatus({ embedModel })` reports 34 embedded, backlog 0. The other `content_vectors` readers (evals/acceptance/eligible-scaling.ts:243, evals/helpers/retrieval-candidate-benchmark.ts:483, evals/fixtures/acceptance/ingestion-identity/oracle.ts) write legacy rows themselves and are correct; `doctor`, `vec` and `status` use the partition path and are correct.

## Acceptance Criteria

- **R1:** Opening an index never deletes a collection or its documents. Read and update paths only upsert the collections their config lists. Deleting a collection's index data happens only through the explicit removal paths (`gno collection remove`/`rename`, MCP/REST remove, `gno cleanup`), which keep their current behavior, except that `gno cleanup` names each collection it is about to drop (text and JSON) before dropping it.
- **R2:** Collections present in the index but absent from the opening config are not searched, listed or returned by that client (no cross-config leakage), and `gno status` names them with the existing `gno cleanup` hint.
- **R3:** `gno agents update` only refreshes harness files that already contain the GNO block; files without one are reported as absent with a `gno agents install` hint and left untouched (no file is created). `install` keeps appending.
- **R4:** `gno skill install`/`uninstall`/`paths` at user scope resolve the Claude target from `CLAUDE_CONFIG_DIR` and the Codex target from `CODEX_HOME` when set (trimmed, non-empty, absolute, as `gno agents` validates them), and print the resolved directory.
- **R5:** A collection whose root is missing or unreadable is named as such by `gno status` (text and JSON: the collection, its path and the root error, with documents kept), by the REST/Web UI status, and by `gno doctor` as a warning (not HEALTHY). Status checks the root at read time, so the report clears as soon as the folder is back, without waiting for the next sync.
- **R6:** `gno search` no longer calls FTS5 `snippet()`; snippets are built only for the final returned rows from their stored chunks, highlighting the query terms, and `snippetRange` is the line span of the chunk the snippet came from. Result order and scores are unchanged for the same query (BM25 eval and existing search tests unchanged). On a copy of a ~2,300-document index, a long natural-language `gno search --json` completes in under 300 ms.
- **R7:** With vectors available, the Web UI's Fast depth runs the same hybrid fast path as CLI `--fast` (`/api/query` with expansion, rerank and graph off; response `meta.mode` hybrid, not expanded, not reranked); without vectors it falls back to `/api/search`. The selector no longer labels Fast as BM25. docs/WEB-UI.md describes Fast/Balanced/Thorough as shipped.
- **R8:** The compact agent projection carries each evidence entry's content date and `supersededBy` (null when absent) as `gno-context-agent-v2`, appended after the existing positions. spec/mcp.md, docs/MCP.md, the `gno_context` tool description, spec/evals-agentic.md, the parity and demo tests and evals/agentic/promotion.ts follow; promotion keeps accepting v1 receipts. Memory facts carry their record date (`memory.createdAt`) as the content date in Capsule evidence and `ask` sources; if that is already true outside the projection, add a test that pins it.
- **R9:** `bun run eval:memory` exits 0 at its 100% gate within 2 minutes, and an eval file that throws makes evalite exit non-zero instead of hanging (patch the pinned evalite reporter with `bun patch`, and report it upstream). Every GNO module that resolves its own path or directory works when `import.meta.path`/`import.meta.dir` are undefined, through one shared helper (file-processor, native-worker client, spa-production-build, sessions import-child, runtime-entrypoint, setup-semantic). A native worker start failure reports its cause, not only "exited".
- **R10:** `evals/ask.eval.ts` calls the model on every case offline: its sources carry the hashes and store content that grounded answers require. The run records a non-zero citation count for at least one preset; the judge stays optional.
- **R11:** The agentic `--write` lane's GNO MCP preparation verifies embeddings through the product's own status (`getStatus({ embedModel })`: no backlog, embedded count equals the active chunk count, an activated vector partition exists) instead of the legacy `content_vectors` table.
- **R12:** Regression tests for R1-R8 (the two-client repro, a CLI `--config` search, cleanup naming, agents update on a file without a block, skill install with `CLAUDE_CONFIG_DIR`, a missing root in status/doctor, snippet order/range parity, the Fast request path, the v2 projection); docs (CLI, SDK, CONFIGURATION, TROUBLESHOOTING, WEB-UI, MCP, skill/agents sections), spec/cli.md, spec/mcp.md, output schemas where JSON shapes change, CHANGELOG, and the gno.sh docs updated.

## Verification

- Two-client test: index collection A, open with a config listing only B, reopen with A: A's documents intact; B's client cannot see A.
- CLI test: `gno --config other.yml search` against an index holding other collections leaves them intact; `gno --config other.yml cleanup --json` names the collections it drops.
- `gno agents update` on a file without a block: unchanged file, absent status. `gno skill install --scope user --target claude` with `CLAUDE_CONFIG_DIR` set writes there.
- Missing root in a sandbox: `gno status` (text/JSON), `GET /api/status` and `gno doctor` name the collection and path; restoring the folder clears it.
- Search timing on a fresh copy of a real index (never the live one): long-question `gno search --json` under 300 ms, results identical to 2.11.0 in order and score.
- Live QA: Web UI Fast on a sandbox index with vectors sends `/api/query` (network capture); MCP `gno_context` text for a Capsule citing a superseded memory fact shows v2 with the successor URI and date.
- `timeout 120 bun run eval:memory` passes at 100%; `bun run eval` with ask.eval shows real generation and citations; the agentic preparation step passes on its fixture.
- `bun run lint:check && bun test`.

## Boundaries

- No change to explicit removal semantics shipped in 2.10.1 beyond cleanup naming what it drops.
- No new config binding or index ownership model unless R1/R2 cannot be met without it.
- No ranking change in this spec: not stopping prefix expansion for short tokens (it changes top-10 order on 3 of 7 measured queries and needs its own eval-gated change), and no work on the balanced preset's missing citation markers (a model/prompt quality question, recorded as a finding).
- No new Web UI depth option; exact-term needs are served by `term` query modes and the command palette.
- QA and tests never open the live index: every script that opens an index passes an explicit `dbPath` or runs under an isolated HOME/XDG environment.
